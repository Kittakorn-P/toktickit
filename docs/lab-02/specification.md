# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

This sprint delivers the Requester-facing half of TokTickIT: a Requester can select a
Development Requester identity, create an IT support ticket with supporting attachments,
locate and review their own tickets through a searchable/filterable My Tickets list, open a
read-only Ticket Detail screen, and manage (add / soft-remove) attachments on their own
tickets — all while one Requester is fully prevented from viewing or modifying another
Requester's data.

## 2. Stakeholder Request Interpretation

IT wants a professional, responsive intake experience so Requesters can submit and track
their own support tickets without needing an IT staff member to do it for them. Since real
login isn't ready until Lab 3, we simulate "being logged in" with a Development Requester
selector so multi-user ownership rules can be built and tested now. The system must
generate official ticket numbers, store everything safely, and — critically — never let one
Requester see or touch another Requester's tickets.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity context)
- Create Ticket (form, validation, attachment upload, submission)
- My Tickets (search, filter, sort, pagination, list/card view)
- Requester Ticket Detail (read-only ticket info + attachment management)
- Attachment lifecycle: upload, view metadata, download, soft-remove
- Ownership enforcement across all Requester-scoped endpoints
- Zen Green reusable UI components (forms, badges, lists, states)

### Excluded
- Real authentication (login, passwords, sessions, tokens, RBAC)
- IT Staff dashboard, queue, ticket claiming/reassignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond initial `New` (resolving, closing, reopening, cancelling)
- Administrator functions (user/role/reference-data management)

## 4. Functional Requirements

- **FR-01** — The system shall allow a user to select an active Development Requester
  before accessing any Requester-scoped screen.
- **FR-02** — The system shall allow the selected Requester to create a new Ticket by
  providing Category, Related System, Summary, Description, Requested Priority, and
  optional Attachments.
- **FR-03** — The system shall generate a unique, backend-assigned Ticket Number upon
  successful Ticket creation.
- **FR-04** — The system shall allow the selected Requester to view a paginated list of
  only their own Tickets.
- **FR-05** — The system shall allow the selected Requester to search their Tickets by
  Ticket Number or Summary text.
- **FR-06** — The system shall allow the selected Requester to filter their Tickets by
  Category, Requested Priority, IT Priority, and Current Status.
- **FR-07** — The system shall allow the selected Requester to sort their Tickets by
  Ticket Number, Created Date, and Last Updated.
- **FR-08** — The system shall allow the selected Requester to open a read-only Ticket
  Detail view for any Ticket they own.
- **FR-09** — The system shall allow the selected Requester to add a permitted Attachment
  to a Ticket they own, up to 5 active Attachments per Ticket.
- **FR-10** — The system shall allow the selected Requester to soft-remove an Attachment
  they own, retaining its metadata but blocking further download/preview.
- **FR-11** — The system shall reject any attempt to view, modify, or attach to a Ticket
  the selected Requester does not own.

## 5. Business Rules

**BR-01** — The official Ticket Number is generated by the backend and must be unique.

**BR-02** — A new Ticket begins with Current Status `New`.

**BR-03** — Lab 2 uses a Development Requester selector instead of login. The selected
identity is for testing only and is not authentication.

**BR-04** — Selecting a Development Requester stores that identity as the current session
context for creating tickets, viewing My Tickets, and accessing Ticket Detail. No
previously loaded ticket data persists across a Requester switch — all Requester-scoped
views must reload from the backend for the newly selected Requester.

**BR-05** — The selected Development Requester is not persisted across page refresh or
new browser sessions; the user must reselect a Requester after a refresh.

**BR-06** — If the currently selected Requester is later deactivated (or no longer appears
in the active Requester list) mid-session, attempts to create or view tickets must fail
safely and redirect the user back to the Requester Selection screen.

**BR-07** — A Requester may only retrieve, view, or modify Tickets and Attachments they
own. Any request for a Ticket (or its Attachments) belonging to a different Requester must
return HTTP 404, presenting no indication that the Ticket exists.

**BR-08** — The Ticket-list endpoint must filter results server-side to only the currently
selected Requester's own Tickets, enforced independently of the frontend.

**BR-09** — Ticket Date, Ticket Number, Ticket Owner, and Current Status are
system-generated at creation time and are never directly editable by the Requester.

**BR-10** — The Ticket list defaults to sorting by Created Date descending (newest first)
when no sort parameter is supplied. Default page size is 10; maximum permitted page size
is 50. Invalid page/sort/filter parameters are ignored and fall back to defaults rather
than causing an error.

**BR-11** — The Submit button is disabled immediately after the first click and remains
disabled until the request completes, to prevent duplicate-submission from double-clicks
or repeated form re-submission.

**BR-12** — If Ticket creation fails after submission (network or server error), all
entered field values and selected attachments must remain populated in the form so the
Requester does not need to re-enter them.

**BR-13** — Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF; maximum size is 5MB
per file; maximum 5 active attachments per Ticket. A rejected file (wrong type or too
large) shows an inline error and is not added to the pending upload list.

**BR-14** — If a Ticket is created successfully but one or more attachment uploads fail,
the Ticket itself remains saved; failed attachments are reported to the Requester with the
option to retry the upload from the Ticket Detail screen.

**BR-15** — Removing an Attachment is a soft removal: the Attachment record and its
metadata remain associated with the Ticket and visible in the Attachment list marked as
Removed, but the file becomes non-downloadable and non-previewable. Only the owning
Requester may remove their own Ticket's Attachments.

**BR-16** — Inactive Development Requesters must not appear in the Development Requester
selector dropdown under any circumstance.

**BR-17** — My Tickets distinguishes between an empty state (the Requester has zero
Tickets at all) and a no-results state (Tickets exist but the current search/filter
combination matches none), with distinct messaging for each.

**BR-18** — Requesting a Ticket Detail page for a Ticket ID that does not exist at all and
requesting one that exists but belongs to another Requester must behave identically
(HTTP 404, generic not-found message), so no information is leaked about which case
occurred.

**BR-19** — The Development Requester Selection screen and its underlying model are
temporary Lab 2 scaffolding. In Lab 3, this mechanism will be replaced entirely by real
authentication (login, sessions, and role-based access), and the selector must be removed
or disabled at that point.

## 6. UI Specification Summary

The application follows the Zen Green Theme (see `ui-spec.md` for full token reference:
primary #006B3C, secondary #0B7A46, pale green #EAF6EF, background #F5F7F6). The shell
includes the TokTickIT header, My Tickets / Create Ticket navigation, and current Requester
display with a Change Requester action. Screens: Requester Selection (dropdown + Continue,
loading/empty/error states), Create Ticket (grouped fields, read-only system-generated
fields visually distinct, busy Submit state, field-level validation messages), My Tickets
(search bar, filter dropdowns, sortable columns, pagination, empty/no-results states),
Ticket Detail (read-only header fields, Attachments panel with active/removed/uploading
states). Responsive breakpoints: desktop ≥992px multi-column, tablet 768–991px two-column,
mobile <768px single-column stacked with touch-friendly controls and no horizontal scroll.

## 7. Data Changes

- **RequesterUser**: id, name, email, isActive, createdAt
- **Category**: id, name (unique), isActive
- **RelatedSystem**: id, name (unique), isActive
- **Ticket**: id, ticketNumber (unique), requesterId (FK → RequesterUser), categoryId (FK),
  relatedSystemId (FK), summary, description, requestedPriority (enum),
  currentStatus (enum, default `NEW`), ticketOwnerId (nullable, for future IT Staff use),
  createdAt, updatedAt
- **Attachment**: id, ticketId (FK → Ticket), originalFilename, storedFilename, mimeType,
  sizeBytes, isRemoved (boolean, default false), removedAt (nullable), removedReason
  (nullable), createdAt

Indexes: unique on `Ticket.ticketNumber`, index on `Ticket.requesterId` (frequently
filtered), index on `Ticket.currentStatus`, unique on `Category.name` and
`RelatedSystem.name`. Foreign keys enforce referential integrity on all relationships
listed in Section 5.1 of the handout.

## 8. API Contract

See `api-spec.md` for full detail. Summary of required endpoints:
- `GET /api/categories` — active Categories
- `GET /api/related-systems` — active Related Systems
- `GET /api/requesters` — active Development Requesters
- `POST /api/tickets` — create Ticket (requires requesterId context)
- `GET /api/tickets?search=&category=&priority=&status=&sort=&page=` — paginated, filtered,
  owned Ticket list
- `GET /api/tickets/:id` — single owned Ticket (404 if not owned or not found)
- `POST /api/tickets/:id/attachments` — upload Attachment
- `GET /api/tickets/:id/attachments` — Attachment metadata list
- `GET /api/attachments/:id/download` — download active Attachment (404 if removed or not
  owned)
- `PATCH /api/attachments/:id/remove` — soft-remove Attachment

Requester identity is passed via an `X-Requester-Id` header on every Requester-scoped
request, validated server-side against the active Requester list.

## 9. Acceptance Criteria

- **AC-01** — Given valid Ticket data, when the Requester submits the form, then one
  Ticket is saved and the official Ticket Number is displayed.
- **AC-02** — Given no Development Requester is selected, when the user attempts to open
  My Tickets, then the Requester Selection screen is shown.
- **AC-03** — Given Requester B is selected, when a Ticket belonging to Requester A is
  requested, then a 404 is returned and no Ticket data is exposed.
- **AC-04** — Given Summary or Description is empty or outside length limits, when the
  Requester submits the form, then field-level validation messages appear and no API call
  is made.
- **AC-05** — Given the Requester double-clicks Submit, when the first request is still
  processing, then only one Ticket is created.
- **AC-06** — Given the backend is unreachable, when the Requester submits a valid form,
  then a safe error state is shown and all entered values remain in the form.
- **AC-07** — Given an attachment exceeding 5MB or an unsupported file type, when the
  Requester selects it, then an inline error appears and the file is not added.
- **AC-08** — Given a Requester has zero Tickets, when they open My Tickets, then an empty
  state (not a no-results state) is shown.
- **AC-09** — Given a Requester has Tickets but a search/filter combination matches none,
  when they view the list, then a no-results state is shown distinct from the empty state.
- **AC-10** — Given an active Attachment on an owned Ticket, when the Requester soft-removes
  it, then it remains visible as metadata but cannot be downloaded or previewed.
- **AC-11** — Given the Requester switches from Requester A to Requester B, when My Tickets
  reloads, then Requester A's Tickets no longer appear.
- **AC-12** — Given a screen is viewed at a mobile viewport (<768px), when the layout
  renders, then no horizontal scrolling occurs and all controls remain usable.

## 10. Definition of Done

- All Functional Requirements (FR-01–FR-11) implemented and demonstrable
- All Acceptance Criteria (AC-01–AC-12, and any added later) pass with automated test
  evidence
- All planned tests in `tests.md` pass from a documented command on the final `main` branch
- No skipped, disabled, or commented-out tests
- Ownership enforcement verified via at least one deliberate cross-Requester test per
  resource type (Ticket, Attachment)
- UI matches `ui-spec.md` at desktop, tablet, and mobile viewports with no clipping,
  overlap, or unintended scrolling
- README setup and test-run instructions are current and accurate
- All Issues reach Done on the Kanban board; PRs reviewed and merged through
  feature branch → `lab2-staging` → `main`

## 11. Assumptions and Decisions

- **404 over 403 for ownership violations** (BR-07, BR-19): chosen to avoid confirming the
  existence of Tickets a Requester doesn't own, minimizing information leakage.
- **Requester identity transport**: `X-Requester-Id` header chosen over a query param, to
  keep it out of URLs/logs and closer to how a future Authorization header would work in
  Lab 3.
- **No persistence of selected Requester across refresh** (BR-05): deliberately weak/manual
  by design, since this selector is temporary scaffolding, not real session management.
- **Field length limits** (BR-11): Summary 5–120 chars, Description 10–2000 chars — chosen
  as reasonable bounds for a support-ticket form; adjust and re-justify if your own testing
  suggests different limits.
